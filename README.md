# Collab Pickup

**Company:** Team Hortons (SOEN 387, Fall 2026, section F)
**Product:** Collab Pickup: a pickup-ordering back-end for shops that sell
limited collab items, combos and bonus gifts.

Every sale draws on one pool of units, whether the item is sold on its own or
inside a combo, so the shop never oversells. Bonus gifts are counted
separately: when they run out, a combo keeps selling and the customer is told
at ordering time that this combo comes without its gift.

This is the **Milestone** version: a running service over its published
contract, with the domain and data layers, the contended resources protected
under concurrency, and JWT authentication.

## Tech stack

FastAPI (Python 3.14) · PostgreSQL 18 · SQLAlchemy (SQL written by hand) ·
psycopg 3 · PyJWT (HS256) · bcrypt · OpenAPI 3.1 generated by FastAPI

## Features (Milestone)

- `GET /menu`: items and combos with live availability; whether each combo still has its bonus gift
- `POST /orders`: place an order; `Idempotency-Key` header required
  - combos are expanded into their items; one stock pool per item
  - per-order limits (e.g. at most 2 Hero Burgers per order, alone or in combos)
  - units are taken from the earliest released batch
  - one bonus gift per combo while gifts last; when gifts run out the order still succeeds with `included: false`
  - the batch rows and bonus-gift rows are locked with `SELECT ... FOR UPDATE` in a fixed order (no overselling, no deadlock)
  - same key + same body → the original response again (`Idempotency-Replayed: true`); same key + different body → `422 IDEMPOTENCY_KEY_REUSED`
- `GET /orders`, `GET /orders/{id}`: your own orders only (someone else's order → `404`)
- `POST /orders/{id}/cancel`: cancel your own order; units go back to their batches, gifts to the gift count
- `POST /items/{id}/batches` (staff only): schedule a release batch
- `POST /auth/login`: username + password → JWT (15 minutes)
- `GET /healthz` (liveness), `GET /readyz` (readiness: can reach the database)
- Test web page at `/` (customer page and staff page)

## Setup (Windows, PowerShell)

### 1. Python environment

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

### 2. Configuration

Copy `.env.example` to `.env` and fill in the values:

| Variable | Meaning |
|---|---|
| `DATABASE_URL` | e.g. `postgresql+psycopg://collab:<password>@127.0.0.1:5434/collab_pickup` |
| `JWT_SECRET` | long random string used to sign tokens |
| `DEMO_PASSWORD` | password that `seed.py` gives to the demo users |

The service refuses to start if `DATABASE_URL` or `JWT_SECRET` is missing.
No secret is stored in the code.

### 3. Database (private PostgreSQL instance on port 5434)

First time only: create the data directory and the database. `initdb` asks for
the password you put in `DATABASE_URL`.

```powershell
& "C:\Program Files\PostgreSQL\18\bin\initdb.exe" -D .pgdata -U collab -W -A scram-sha-256 -E UTF8 --locale=C
.\db.ps1 start
& "C:\Program Files\PostgreSQL\18\bin\createdb.exe" -h 127.0.0.1 -p 5434 -U collab collab_pickup
```

After that:

```powershell
.\db.ps1 start      # or: stop, status
```

### 4. Migrations and demo data

```powershell
python migrate.py   # applies migrations/*.sql in order; safe to run again
python seed.py      # resets all data to the demo menu and users
```

Demo users: `alice`, `bob` (customers) and `staff` (staff), all with `DEMO_PASSWORD`.
Demo menu: Hero Burger (limited, max 2 per order; 10 on sale now, 6 more in a
batch that opens tomorrow), Blue Soda (limited, 10), Fries (unlimited), and
the Hero Set combo (burger + soda) with 3 bonus gifts.

### 5. Run the service

```powershell
uvicorn app.main:app --host 127.0.0.1 --port 8000
```

- Test page: http://127.0.0.1:8000/
- Interactive contract: http://127.0.0.1:8000/docs
- Use `127.0.0.1`, not `localhost`: on Windows `localhost` tries IPv6 first and adds about 2 s to each request.

**One-click start (after the one-time setup in steps 1–3):** double-click
`start.bat`. It starts the database if needed, applies new migrations, asks
whether to reset the demo data (No after 5 seconds), opens the test page and
runs the service; Ctrl+C stops the service. `stop.bat` stops the database.

To refresh the contract file after changing the API: `python scripts/export_openapi.py`.
`tests/test_contract.py` fails until you do, so the committed contract never
falls behind the code.

## Demo scripts

All three reset the database to the demo data first.

```powershell
python scripts/race.py unsafe     # no row locks: 100 orders for 10 burgers -> oversold
python scripts/race.py locked     # FOR UPDATE: exactly 10 sold, remaining 0, 3 gifts given
```

`race.py` calls the service layer directly with 100 threads (half order a
Hero Burger, half a Hero Set). The `unsafe` path is the same code without
`FOR UPDATE`, kept only as the control group. A sample run is in
`race_output.txt`.

The next two need the service running:

```powershell
python scripts/double_submit.py   # 8 identical requests with one key -> one order, 7 replays; new body -> 422
python scripts/attacks.py         # tampered token -> 401, alg=none -> 401, Bob vs Alice's order -> 404
```

## Running the tests

```powershell
python -m pytest -q
```

| File | What it tests | Needs |
|---|---|---|
| `tests/test_domain.py` | every business rule in `domain.py` on plain objects | nothing |
| `tests/test_service_memory.py` | the use cases on the in-memory repository: order, replay, key reuse, ownership, cancel | nothing |
| `tests/test_service.py` | the same use cases on the real database | PostgreSQL running |
| `tests/test_api.py` | the HTTP layer with FastAPI's TestClient: 401, 403, 400, the error shape | nothing (requests are refused before the database) |
| `tests/test_contract.py` | the committed `openapi.json` equals the contract the code generates | nothing |

`test_service.py` resets the database to the demo data before each test, so it
erases any orders you placed by hand. A sample run is in `test_output.txt`.
The concurrency itself is tested by `scripts/race.py` (see above).

## Conformance check (Schemathesis)

Schemathesis reads the running service's contract, generates hundreds of
requests for every operation (valid and invalid), and checks that no
response is a 5xx and that every response body matches the contract's
schema. With the service running:

```powershell
python scripts/conformance.py
```

It logs in as `alice`, saves the report to `conformance_output.txt`, and
resets the demo data afterwards (it places many orders). Two warnings in the
report are expected: random usernames get 401 and Alice gets 403 on the
staff-only route; and most generated order lines name items that are not on
the menu (422 `UNKNOWN_ITEM`), because the menu is data, not part of the schema.

## Error model

Every error has the same shape:

```json
{ "error": { "code": "SOLD_OUT", "message": "...", "details": { "itemId": "burger-hero" } } }
```

| Status | Code | Retry? |
|---|---|---|
| 400 | `VALIDATION_ERROR` (bad JSON, missing field or header, qty < 1, ...) | No: fix the request |
| 401 | `UNAUTHENTICATED`, `INVALID_TOKEN` | After logging in again |
| 401 | `INVALID_CREDENTIALS` | No |
| 403 | `FORBIDDEN` (wrong role) | No |
| 404 | `ORDER_NOT_FOUND` (also for someone else's order), `ITEM_NOT_FOUND`, `HTTP_ERROR` | No |
| 409 | `SOLD_OUT` | Not with the same key (it replays `SOLD_OUT`); order later with a new key |
| 409 | `ORDER_NOT_CANCELLABLE` | No |
| 422 | `PER_ORDER_LIMIT`, `UNKNOWN_ITEM` | No: change the order and use a new key |
| 422 | `IDEMPOTENCY_KEY_REUSED` | No: a new request needs a new key |
| 422 | `BATCH_NOT_ALLOWED` | No |
| 500 | `INTERNAL_ERROR` | Yes, with the **same** Idempotency-Key: it replays or places the order once |

The same catalog, with what a client should do for each code, is in the
description of `openapi.json` (shown at the top of `/docs`).

## Concurrency design in one paragraph

Placing an order is one transaction at `READ COMMITTED`. It expands combos,
checks per-order limits, then locks the released batch rows of the needed
items (`ORDER BY item_id, release_at, id FOR UPDATE`) and then the combo's
bonus-gift row (`ORDER BY combo_id FOR UPDATE`). It checks stock, takes
units, writes the order, and writes the idempotency record with
`INSERT ... ON CONFLICT DO NOTHING`, all before one commit. Because every
transaction (including cancel) takes its locks in the same order, two orders
can never wait on each other in a circle. The `CHECK (remaining >= 0)`
constraints are a last line of defence in the database.
